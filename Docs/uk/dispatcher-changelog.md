# Канал диспетчера — журнал змін

[English](../dispatcher-changelog.md) · **Українська**

Зміни каналу `[dispatcher]` у цьому форку (гілка `feature/dispatcher-link`). Бік платформи:
[CHANGELOG flowstation-platform](https://github.com/hbohatix/flowstation-platform/blob/main/CHANGELOG.uk.md).

## Протокол v3 — 2026-10-25 (платформа 0.6.0)

- Новий `NodeToCore::BackhaulStatus { brew_configured, brew_connected }`, що надсилається з
  кожним `NodeStatus` (після Hello і кожні 10 с): чи є в станції секція `[brew]` і чи підключено
  Brew (`network_connected` у стані стека). Консоль показує це як стан Brew станції. Лише
  читання: у бік Brew нічого не надсилається.
- Станція оголошує протокол 3. Потрібен core платформи 0.6.0 або новіший; core і далі приймає
  станції v2, тож станції можна оновлювати по одній.

## Типи шини — 2026-10-25 (платформа 0.5.0)

- `crates/dispatch-proto/src/bus.rs` повторює платформу: новий `CoreEvent::NodeLink { rtt_ms }`
  (RTT QUIC від core до станції, показується в консолі як пінг станції). Тип лише для шини між
  сервісами платформи; протокол станція↔core не змінився (і далі v2), тож станції оновлювати не
  потрібно.

## Протокол v2 — 2026-10-25

- Для платформи прослуховується кожен груповий виклик (`MonitorSet { all }`), разом із мережевими
  мовцями: CMCE повідомляє каналу про мовців Brew/SIP, UMAC копіює йому мережевий голос
  низхідного каналу. Лише прийом — у бік Brew нічого не надсилається.
- Команди радіостанціям із консолі: kick (CMCE `KickMs`), перереєстрація (MM D-LOCATION UPDATE
  COMMAND із запитом звіту груп, нова команда керування `ReRegister`), запит позиції (LIP
  IMMEDIATE LOCATION REPORT REQUEST як SDS типу 4, TS 100 392-18-1 §6.2.16).
- Список банів для всієї мережі в `Settings`: зберігається в стані стека (`issi_banlist`),
  перевіряється MM під час реєстрації, приєднання до групи та реактивного відновлення;
  зареєстровані забанені радіостанції відключаються.
- `NodeStatus` кожні 10 с (час роботи, несучі, MCC/MNC/LA, зареєстровані радіостанції, виклики,
  таймслоти, температура CPU); `SettingsApplied.banned`.
- Повний стан (радіостанції, групи, останні позиції) після кожного (пере)підключення і на `ResyncState`.

## Постійне відновлення — 2026-10-24

- Станція з `[dispatcher]` завжди виконує відновлення після перезапуску (`recovery_cache.json`).
- Команди відновлення повторюються приблизно щосекунди (один мультикадр), а не кожен кадр, тож
  радіостанцію, зайняту на каналі трафіку, все одно буде досягнуто після виклику; невідома
  радіостанція, помічена у висхідному каналі, отримує повтори, доки не перереєструється.
- Диспетчерські виклики йдуть в ефір, навіть коли станція не знає жодного слухача групи, і не
  обриваються, коли відключається останній відомий слухач.
- Витісняючий (12–15) виклик диспетчера звільняє виклик із нижчим пріоритетом на групі та
  встановлює власний замість продовження як зміни мовця (EN 300 392-2 §14.8).
- Новий PTT, поки власна попередня передача диспетчера відтворює буфер, замінює її, а не
  отримує відмову `FloorBusy`.

## Протокол v1 — 2026-10-24

- DGNA і текстові SDS з консолі через канал керування CMCE; позиції, RSSI, стан DGNA та отримані
  SDS повідомляються платформі.

## Етап 0 — 2026-10-23

- Канал QUIC/TLS до core платформи, групові виклики диспетчера з пріоритетом, прослуховування,
  захист від Brew у трьох шарах, відтворення буфера перед hangtime.
