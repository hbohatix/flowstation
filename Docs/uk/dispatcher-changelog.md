# Канал диспетчера — журнал змін

[English](../dispatcher-changelog.md) · **Українська**

Зміни каналу `[dispatcher]` у цьому форку (гілка `feature/dispatcher-link`). Бік платформи:
[CHANGELOG flowstation-platform](https://github.com/hbohatix/flowstation-platform/blob/main/CHANGELOG.uk.md).

## Протокол v5: статуси, причини LIP, звіти доставки SDS — 2026-10-26 (платформа 0.8.0)

- SDS і статуси на ISSI диспетчера завершуються на станції (ніколи не в Brew): станція надсилає
  звіт доставки SDS-TL, який просить радіостанція (EN 300 392-2 §29.4.2.2 — delivery status 0
  «отримано» / 2 «прочитано»), і закриває статус луною D-STATUS (§14.7.1.11; не для тривоги).
  ISSI диспетчера зберігається у стані стека для CMCE.
- Кожен закодований статус іде на платформу (`StatusReceived`), консоль може надіслати статус
  (`SendStatus` → D-STATUS на ISSI чи GSSI).
- LIP: кожен звіт іде на платформу як `MsLocation` з причиною; звіти з «position error not
  known» (TS 100 392-18-1 табл. 6.1 прим. 4), довгі звіти з «no shape» (тепер декодуються) і 0/0
  не мають позиції — і більше не ставлять радіостанцію в 0°/0° на дашборді станції.
- `AckEmergency`: консоль підтверджує тривогу — D-STATUS Emergency з адреси призначення тривоги
  до радіостанції, що зупиняє її повтори *console acknowledge*.
- `EmergencyEnded { by }`: радіостанція (звичайний статус), тайм-аут або оператор, тож консоль не
  показує тайм-аут як скасування радіостанцією.

## Диспетчер на кожній локальній групі, протокол v4, без обриву виклику — 2026-10-25 (платформа 0.7.0)

- `[dispatcher] local_groups` (типово `true`): диспетчер може передавати на кожній лише локальній
  групі (`cell.local_ssi_ranges`; на кожній, якщо `[brew]` немає), а не лише зі списку `gssis`.
  Групи, що йдуть у Brew, і далі відхиляються (`gate_call`), а диспетчерські групи ніколи не
  оголошуються в Brew.
- Протокол v4: `StationInfo` з кожним `NodeStatus` — repeater ID (username у `[brew]`), хост Brew,
  код кольору, сусідні комірки та діапазони, за якими core маршрутизує PTT диспетчера. Потрібен
  core платформи 0.7.0 (приймає v2–v4).
- CMCE більше не обриває живий виклик, коли оновлення місцезнаходження радіостанції зі звітом груп
  приходить як «від’єднати всі + приєднати звітовані»: група має лишатися без слухачів одну
  мультифрейм (близько 1 с), перш ніж її виклики обриваються. Раніше радіостанція замовкала посеред
  виклику, а консоль його ще чула (напр. після D-LOCATION UPDATE COMMAND при кожному
  перепідключенні Brew).

## PHY: вихід із зупинки таймлайну TX — 2026-10-25

- Після збою SDR/USB (переповнення буфера RX) бік RX міг тримати запас буферизованих відліків і
  читати його точно в темпі реального часу безкінечно. Модулятор отримує нові біти слоту лише раз
  на слот RX, тож кожен блок TX запізнювався і пропускався: комірка переставала передавати («No
  service») до перезапуску станції (2026-10-25, 90 000 попереджень за 3,5 хв).
- Новий `phy/components/tx_watchdog.rs`: якщо TX 0,5 с нічого не видав, запізнюючись, PHY скидає
  запас RX і продовжує від поточного годинника SDR (не частіше ніж раз на 2 с). Попередження
  показує, наскільки RX відставав. Один раз втрачається близько 100 мс висхідного каналу, а не комірка.
- «Too late to produce TX block» пишеться раз на 5 с із кількістю запізнілих блоків, а не на кожен
  блок (сам потік повідомлень уповільнював потік PHY).

## Протокол v3 — 2026-10-25 (платформа 0.6.0)

- Новий `NodeToCore::BackhaulStatus { brew_configured, brew_connected }`, що надсилається з
  кожним `NodeStatus` (після Hello і кожні 10 с): чи є в станції секція `[brew]` і чи підключено
  Brew (`network_connected` у стані стека). Консоль показує це як стан Brew станції. Лише
  читання: у бік Brew нічого не надсилається.
- Станція оголошує протокол 3. Потрібен core платформи 0.6.0 або новіший; core і далі приймає
  станції v2, тож станції можна оновлювати по одній.

## Типи шини — 2026-10-25 (платформа 0.5.0)

- `crates/dispatch-proto/src/bus.rs` повторює платформу: новий `CoreEvent::NodeLink { rtt_ms }`
  (RTT QUIC від core до станції, показується в консолі як пінг станції). Тип лише для шини між
  сервісами платформи; протокол станція↔core не змінився (і далі v2), тож станції оновлювати не
  потрібно.

## Протокол v2 — 2026-10-25

- Для платформи прослуховується кожен груповий виклик (`MonitorSet { all }`), разом із мережевими
  мовцями: CMCE повідомляє каналу про мовців Brew/SIP, UMAC копіює йому мережевий голос
  низхідного каналу. Лише прийом — у бік Brew нічого не надсилається.
- Команди радіостанціям із консолі: kick (CMCE `KickMs`), перереєстрація (MM D-LOCATION UPDATE
  COMMAND із запитом звіту груп, нова команда керування `ReRegister`), запит позиції (LIP
  IMMEDIATE LOCATION REPORT REQUEST як SDS типу 4, TS 100 392-18-1 §6.2.16).
- Список банів для всієї мережі в `Settings`: зберігається в стані стека (`issi_banlist`),
  перевіряється MM під час реєстрації, приєднання до групи та реактивного відновлення;
  зареєстровані забанені радіостанції відключаються.
- `NodeStatus` кожні 10 с (час роботи, несучі, MCC/MNC/LA, зареєстровані радіостанції, виклики,
  таймслоти, температура CPU); `SettingsApplied.banned`.
- Повний стан (радіостанції, групи, останні позиції) після кожного (пере)підключення і на `ResyncState`.

## Постійне відновлення — 2026-10-24

- Станція з `[dispatcher]` завжди виконує відновлення після перезапуску (`recovery_cache.json`).
- Команди відновлення повторюються приблизно щосекунди (один мультикадр), а не кожен кадр, тож
  радіостанцію, зайняту на каналі трафіку, все одно буде досягнуто після виклику; невідома
  радіостанція, помічена у висхідному каналі, отримує повтори, доки не перереєструється.
- Диспетчерські виклики йдуть в ефір, навіть коли станція не знає жодного слухача групи, і не
  обриваються, коли відключається останній відомий слухач.
- Витісняючий (12–15) виклик диспетчера звільняє виклик із нижчим пріоритетом на групі та
  встановлює власний замість продовження як зміни мовця (EN 300 392-2 §14.8).
- Новий PTT, поки власна попередня передача диспетчера відтворює буфер, замінює її, а не
  отримує відмову `FloorBusy`.

  SDS повідомляються платформі.
